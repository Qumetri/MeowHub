# n8n

Workflow automation — schedule or webhook triggers wired to HTTP calls, local or
hosted LLMs, and notifications. Optional: enable the `n8n` profile.

```bash
# .env
COMPOSE_PROFILES=nextcloud,immich,n8n,ollama
```

| | |
|---|---|
| Web UI | `https://${BASE_DOMAIN}/${N8N_PUBLIC_PATH}/` |
| Loopback | `http://127.0.0.1:${N8N_LOCAL_PORT}/${N8N_PUBLIC_PATH}/` |
| Data | `n8n/data/` (sqlite) |
| Workflow exports | `n8n/workflows/*.json` |

**Auth is n8n's own account login**, not basic_auth. Every other secret-path
service here sits behind Caddy basic_auth because it has no login of its own;
n8n does, with optional TOTP 2FA — turn it on. A second credential prompt would
also interfere with the websocket the editor uses for live execution updates.

> `N8N_ENCRYPTION_KEY` (generated by `bootstrap.sh`) encrypts every credential
> stored in n8n's database. **Back it up with `.env`.** Losing it does not lose
> the workflows, but every saved credential becomes unreadable.

## The subpath, and how it fails

n8n's docs warn that combining `N8N_PATH` with a reverse proxy "can cause folder
navigation issues". They are right, and the reason is specific:

> **`N8N_PATH` changes the URLs n8n *generates*, not where it *serves* from.**
> The HTML asks for `/{prefix}/static/base-path.js`; the file is mounted at
> `/static/base-path.js`.

The two settings are complements, not duplicates:

- n8n adds the prefix to every URL it emits (`N8N_PATH`).
- Caddy takes the prefix off again with **`handle_path`** before proxying.

Using `handle` (prefix preserved) produces a **blank page**, and does so
silently: n8n answers *any* unrecognised path with the SPA shell, so
`/{prefix}/static/base-path.js` returns **200 `text/html`** instead of 404.
Every asset "works" by status code while the browser receives HTML where it
expects JavaScript, `window.BASE_PATH` is never defined, and nothing mounts.

**Check content types, not status codes:**

```bash
curl -sI https://${BASE_DOMAIN}/${N8N_PUBLIC_PATH}/static/base-path.js | grep -i content-type
# text/javascript  -> correct
# text/html        -> the SPA fallback; the page will render blank
```

## Local models

The `ollama` profile adds a model runtime that n8n reaches as
`http://ollama:11434`. It **publishes no port**: an unauthenticated model server
should not be listening on the network, and nothing outside the compose network
needs it.

Models go to `OLLAMA_MODELS` (default `${DATA_ROOT}/ollama`) — they are large,
and they do not belong on the system disk.

GPU is opt-in:

```bash
# .env
COMPOSE_FILE=docker-compose.yml:docker-compose.gpu.yml
```

Without it Ollama runs on the CPU: usable for a nightly job, painful for
anything interactive.

Sizing, for a 12 GB card (checked 2026-09):

| Model | Disk | Fit |
|---|---|---|
| `qwen3:8b` | 5.2 GB | fully in VRAM, ~60 tok/s — the default fallback |
| `gemma4:12b` | ~8 GB | fully in VRAM; newest dense model that fits, strong multilingual |
| `qwen3.6:35b-a3b`, `gemma4:26b-a4b`, `nemotron-3.5-lightning:30b` | 16–25 GB | MoE: only 3–4B parameters are active per token, so offloading part of the weights to system RAM stays usable (needs ~32 GB RAM) |
| 27B+ dense | 17 GB+ | every token reads every weight — spills to RAM and crawls |

```bash
docker compose exec ollama ollama pull qwen3:8b
docker compose exec ollama ollama list
```

**Watch the disk.** Ollama preallocates blobs as *sparse* files while
downloading, and an aborted pull leaves a `*-partial` blob behind. Those report
an enormous apparent size while occupying much less, so `du --apparent-size`,
backup tools and naive copies all wildly overstate them:

```bash
# real disk use vs apparent size
du -sh  "$OLLAMA_MODELS"; du -sh --apparent-size "$OLLAMA_MODELS"
# abandoned downloads, safe to delete when nothing is pulling
find "$OLLAMA_MODELS/models/blobs" -name '*-partial*' -delete
```

Copy that directory with `rsync -aS` (or `cp --sparse=always`). Without
`--sparse` the holes are written out as real blocks and a 7 GB directory can
become hundreds of gigabytes.

## The bundled workflow

`n8n/workflows/crypto-daily-summary.json` — import it from the n8n UI
(**Workflows → Import from File**). Needs the `crypto` profile.

```
09:00 / Test manually
   → Get digest            GET crypto:9102/api/digest — 24h stats + last-24h news
   → Build prompt          numbered headlines, per-coin facts, JSON shape
   → OpenRouter            hosted model, 3 tries
        ├ ok   → Valid answer? → Use it ─┬ true  → Compose message
        │                                └ false ─┐
        └ error ─────────────────────────────────┴→ Ollama qwen3:8b (fallback) → Compose
   → Send to Telegram      one or more messages
```

Each coin gets a heading printed **by code** — price, 24h change, "with / stronger
/ weaker than the market" — then one or two sentences from the model: what
happened inside the day (sharpest hour, range, alerts) and **why, only if a
headline supports it**. News comes from the tracker's `/api/digest` (Google News
per coin, crypto outlets, and the exchanges' own announcements — see
[CRYPTO.md](CRYPTO.md)).

Rules that keep it honest:

- **The model never supplies a number.** Every figure is computed by the tracker
  from its own candles and printed by code.
- **A reason must cite a numbered headline as `[n]`.** *Compose* turns it into a
  link and **drops any number that does not exist**, so an invented source never
  reaches the message.
- **No headline, no reason** — small coins often have none, and the summary says so.
- Alerts are *what happened*, never a *reason*.

**Why a hosted model is primary.** On the same prompt, `qwen3:8b` called a coin
that beat the market by 2.7pp "lagging" and blamed a rise on "selling pressure";
Nemotron 120B (OpenRouter, free tier) got both right and cited the actual ETF
news. The local model stays as the **fallback**: free models regularly answer
429, or HTTP 200 with an error body — *Valid answer?* catches that — and a
weaker summary beats none. The footer names the model that wrote it.

### Before the first run

1. **OpenRouter** node → create an *OpenRouter* credential with a free key from
   openrouter.ai. Without one the node errors and every run uses the local model.
2. **Send to Telegram** → create a Telegram credential, replace
   `PUT_YOUR_CHAT_ID_HERE` with your chat id (the crypto tracker's Telegram tab
   can discover it).
3. Pull the fallback model: `docker compose exec ollama ollama pull qwen3:8b`.
4. **Test manually → Execute workflow**, then **Publish**.

OpenRouter free-model limits: 20 requests/minute, **50/day**; after buying
**≥ $10** of credits, **1,000/day**. Free models do not spend the credits. The
summary uses 1–3 requests a day.

### Pitfalls

- **A literal `}}` inside an n8n `{{ }}` expression ends it** — the node fails
  with a bare `invalid syntax`. Build JSON strings in a Code node instead.
- **A disabled node passes its input through.** Never park an alternative model
  node in parallel "disabled"; it feeds the raw prompt downstream.
- The credential the n8n *Assistant* wizard creates is not shareable with
  workflows ("does not have access to the credential") — create a separate one.

## The move-explainer workflow

`n8n/workflows/crypto-move-explainer.json` — called by the crypto tracker right
after a volatility alert, it answers **as a reply under the alert** with the
likely cause. Setup is in [CRYPTO.md](CRYPTO.md) (*Why did it move*).

```
Webhook  POST /webhook/crypto-move, Header Auth X-Hook-Secret, answers 202 at once
   → Get digest            crypto:9102/api/digest?fresh=1
   → Build prompt          the move; market-vs-coin decided in code; headlines with age
   → OpenRouter → Valid answer? → Use it → (Ollama qwen3:8b fallback) → Compose
   → Reply under the alert  Telegram reply_to_message_id = the alert's message
```

Whether the whole market moved or just this coin is **computed**, from the share
of tracked coins that moved ≥1% the same way within the hour — the model is told
the verdict, not asked for it. Each headline carries its age, because a day-old
story rarely explains a sharp hour.

## Operations

```bash
docker compose logs -f n8n
docker compose up -d n8n
```

Export a workflow back to the repo:

```bash
docker compose exec n8n n8n export:workflow --id=<id> --output=/tmp/wf.json
docker compose cp n8n:/tmp/wf.json n8n/workflows/<name>.json
```

`n8n execute --id <id>` needs a **Manual Trigger** in the workflow (a Schedule
Trigger alone gives `Missing node to start execution`), and needs the task broker
moved aside so it does not collide with the running instance:

```bash
docker compose exec -e N8N_RUNNERS_BROKER_PORT=5699 -e N8N_PORT=5699 n8n \
  n8n execute --id <id>
```

There is no `delete:workflow` CLI command — delete from the UI.

## Backups

`n8n/data/database.sqlite` holds the workflows, the execution history and the
**encrypted credentials**; `.env` holds the key that decrypts them. Back up both
or neither — either alone will not restore a working instance.
